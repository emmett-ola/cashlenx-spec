### Retained Server Repair And Database Boundary

The existing Testing repair omits unset MongoDB verification tokens so the
sparse unique index can accept multiple pending codes. Server `develop` now
contains this previously Testing-only implementation. The cumulative source
diff from Server `origin/main` (`b799edc`) adds migration
`018_omit_empty_verification_tokens.js` and its Go handler; it must not use the
original App-only database-unchanged classification.

- Classification: forward-compatible MongoDB data repair. MySQL migration
  assets and the OpenAPI contract are unchanged.
- Ordered MongoDB identities: `001`, `010`, `016`, `017`, `018`. Migration
  `018` SHA-256 is
  `b8677b10fbe804596657b1bad7f2f8a0f705fdea346d0bf393a8c4272a6fe930`.
- Existing-data behavior: remove only fields whose `verification_token` is the
  empty string. Non-empty tokens remain unchanged. Repeating the cleanup
  matches no previously cleaned field; the migration runner tracks immutable
  ordered checksums and completion state.
- Runtime rollout remains pending and separate: verify a recoverable database
  backup and the complete ledger before any affected Server deployment; the
  migration runner applies required handlers on startup. Source reconciliation
  does not show whether a Testing or Production database already ran `018`.
- Recovery: retain the migration identity and use a reviewed forward repair or
  verified database restore. An older binary can write empty fields again;
  code rollback alone does not undo or establish safe database recovery.
- Existing mapper tests cover absent and non-empty tokens. The tagged MongoDB
  integration test seeds an empty token and checks cleanup. Prior Server CI and
  API Smoke passed for `584cd33` on Testing; that evidence does not replace the
  full upgrade, repeat, checksum, dirty-state, backup, restore, and recovery gate.
