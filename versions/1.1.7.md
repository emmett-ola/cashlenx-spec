## The corrected model

| Area | How it reaches production | What is maintained |
| --- | --- | --- |
| App | GitHub CI on `main` builds the Flutter Web bundle and publishes it to `emmett-ola/cashlenx-app-release-main`; Vercel serves that repository with no build step. `testing` publishes to `cashlenx-app-release-test`. | `.github/workflows/ci.yml`, the release-repository token, the build entry points. |
| Website | GitHub CI builds; Vercel deploys the Website repository. | `.github/workflows/ci.yml`, `scripts/build.sh`, the Bun lockfile. |
| Server | No automated deployment. The owner runs the repository's own `scripts/build.sh` and `scripts/start.sh` on the Linux host, in dependency order. | Those lifecycle scripts and `scripts/lib/container_lifecycle.sh`. |

Keep GitHub CI and the shell scripts working; publishing what they produce stays
the owner's act. `spec/` ships no deployment automation, and the five retained
PowerShell entry points deleted in `1.1.5` were never part of this path.

Rewritten for the corrected model: `facts/operations.md` §Delivery surfaces
(including the Server's manual sequence on the Testing host, restored with its
health, ingress-reload and stop-preserves-data rules), `facts/delivery.md`
§Main promotion, one principle, and the matching `AGENTS.md` rule.
